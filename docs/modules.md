# 模块讲解与面试问答

这些是帮助理解的讲法，不是让你冒充完全独立原创。先复现每个失败案例，再用自己的语言讲设计取舍。源码路径均相对仓库根目录。

## 1. 数据与版本：给每次改动留证据

**业务问题**：把会话放在 Python 字典里，重启就丢失；直接覆盖 Skill，出错无法回滚。同名 Skill 也不一定是同一业务对象。

**输入/输出**：上传文本文件 → Skill ID、Version ID、Workspace ID；运行报告 → Run；验证/发布 → Decision；前端恢复 → 数据库中的快照。

**代码导航**：`store.py` 的 `Skill / Version / Suite / Run / Job / JobEvent / Decision / Workspace`；`Store.save()` 负责短事务；`Store.publish()` 将资格检查、指针更新、审计写入放在同一个事务。

**例子/失败**：上传两个同名 code-reviewer 会产生两个 Skill ID；给既有 Skill 上传新版本需要显式 skill_id，且元数据身份保持不变。发布 V2 后回滚 V1，不覆盖 V2 文本，而是移动 `current_version_id`。从未发布的草稿不能回滚。

**设计取舍**：SQLite/WAL 与 SQLModel 足够支持本地单进程原型，少一个数据库服务。业务 ID 归属检查由 API/发布事务完成；目前没有完整外键约束、迁移框架和多租户权限，不能宣称生产级数据库治理。

**30 秒讲法**：我把内存会话改成持久化业务记录，每次 Skill 修改都保存独立版本，评测结果绑定版本和评测集。发布只是移动版本指针，并和审计一起提交，回滚不会覆盖历史内容。

**2 分钟讲法**：先解释 Skill 与 Version 的区别，再解释 Workspace 不是模型聊天 Session。用一次“上传 → 候选 → 评测 → 发布 → 回滚”的记录串起来。重点说为什么不是一个 status 字段：Version 管快照资格，Job 管任务运行，Decision 管验证/人工操作。最后说明单进程限制和 SQLite 取舍。

**常见问答**：

1. 同名为什么不合并？名称不是稳定的业务主键，自动合并会串数据。
2. 为什么保存完整快照而不是只保存 diff？下载/复测不依赖递归还原，原型数据量小。
3. 回滚是否删除新版本？不删除，只切指针并记录 previous_id。
4. 重启正在跑的任务怎么办？标记 interrupted，让用户重新启动，不自动重复计费调用。
5. 多进程安全吗？当前任务约束不跨进程；上线前需持久队列、分布式互斥和权限。

## 2. 固定评测集：考试题先确认，再改答案

**业务问题**：不知道用户会上传什么 Skill，就不能用一套通用题评所有 Skill；如果每轮重新生成题，分数变化不能代表版本变化。

**输入/输出**：该 Skill 正文/引用 → Designer 草稿或用户 JSON → Pydantic 校验 → 人工确认的 Suite ID + hash。

**代码导航**：`domain.py` 的 `Criterion / Case / SuiteInput.confirm()`；`app.py` 的 `analyze / save_suite / confirm`；`examples.py` 只提供离线体验数据。

**例子/失败**：代码审查题的输入是一个具体函数，而不是“请审查代码”；其中 keyword 检查格式、llm 检查建议是否针对输入、forbidden 检查秘密泄漏。Case 直接拥有自己的 checks，不做所有题与所有标准的笛卡尔积。同一输入不能同时出现在 train 和 holdout。

**设计取舍**：最低 5 train + 3 holdout 是工程校验的起点，不是科研充分样本量。只检查完全相同的输入，不做语义去重。草稿生成也可能出题质量差，必须人工审查。编辑 JSON 比复杂拖拽设计器简单，适合先学习模型。

**30 秒讲法**：评测集按 Skill 建立，先生成或导入草稿，再人工确认冻结。场景绑定自己的标准，区分训练和保留输入；优化过程中不变题，保存 Suite 版本和 hash 保证可追溯。

**2 分钟讲法**：先举“写作 Skill 不能用 SQL 题来评”的例子，说明专属草稿。接着讲 Case 和 Criterion 两层结构，为什么安全检查单独标记。再说 train 用于给优化器反馈，holdout 用于最后验证。最后承认模型出题、完全重复检测和小样本的局限。

**常见问答**：

1. 固定是不是所有用户都用同一套题？不是，每个 Skill 有自己的固定版本。
2. 模型生成后为什么还确认？模型不知道业务底线，人要检查可判定性和覆盖范围。
3. 冻结后想改怎么办？生成新 Suite，保留旧结果和旧 hash。
4. holdout 永远能重复使用吗？不能无限适配它；跨任务反复试错也会泄漏，应轮换独立集。
5. 为什么两组都要安全标准？只在训练题安全，不代表未见输入也安全。

## 3. 评测器：把“给个分”变成完整判题

**业务问题**：LLM Judge 可能漏判、重复 ID、返回字符串 true；如果只计算返回结果，会虚高分。

**输入/输出**：Skill、引用、Case 列表 → Executor 输出 → 规则/语义逐项结果 → 功能分、安全分、错误数、完整证据。

**代码导航**：`evaluation.py` 的 `Evaluator.run / judge / rule_check / summarize`；`domain.py` 的 `Judgment / Judgments`。

**例子/失败**：一个场景期望 4 个 checks，Judge 少返回 1 个语义 ID，系统要求修复一次；仍不合法，则这个场景记 error，4 个预期检查都进入分母，不能只拿成功项算分。禁止字符串 `"true"` 代替布尔值。

**设计取舍**：keyword/forbidden/JSON Schema 可直接判的由代码判；语义标准才交给 Judge。Judge 和执行器独立角色、独立 Session，但默认同一模型，仍可能存在相关偏差；不是多模型投票。Judge 响应错误时整个场景 fail-closed，较保守。

**30 秒讲法**：确定性规则和独立语义 Judge 分工，所有结果都按预期标准计分。评分响应必须覆盖全部 ID、每项只出现一次、passed 必须是 bool；错误修复一次后仍失败就记 error，保存输入输出和理由便于追查。

**2 分钟讲法**：用一个场景讲执行输出如何进入 Judge。展示保存的 criterion、reason 字段，再解释严格结构校验解决了哪些错误。功能分和安全分分开算，安全不能被平均抵消。最后说为什么角色分离不等于模型完全独立，后续需要人工标注校准 Judge。

**常见问答**：

1. 为什么不用模型判所有规则？确定性判定更便宜、可复现，也不会受输出指令影响。
2. error 和 failed 有何区别？failed 是有效判定不达标；error 是没有可信判定，发布也被阻断。
3. 分母是什么？所有预期 checks，不是模型返回了多少条。
4. 独立 Judge 就客观了吗？没有，同模型和提示偏差仍要测，安全规则也只覆盖已知风险。
5. 能直接比较不同评测集的分数吗？不能当成同一实验；当前每次基线和候选使用同一冻结 Suite。

## 4. 优化器：只把失败训练证据交给修改者

**业务问题**：只发“总分 60”给 Analyst，很难知道哪项标准错；Agent 看到保留题，会针对考试题优化。

**输入/输出**：起始 files、train cases、max_rounds、评测/保存回调 → 最佳内容、初始/最终训练报告、每轮保留记录。

**代码导航**：`adk_optimizer.py` 的 `Agents.ask / real / json / demo`、`SkillOptimizer.optimize()`。`jobs.py` 负责传入 train，而不是整套 Suite。

**例子/失败**：失败检查包含原输入、实际输出、标准与理由；Analyst 返回诊断和一种策略；Mutator 收到诊断并返回完整新正文。元数据改变、引用文件丢失、内容没有变化会被拒绝。正文里要求“单点修改”是 Prompt 约束，目前不能形式化证明语义上只改了一件事。

**设计取舍**：不用新框架包一层图；普通 async 函数足以表达顺序。每轮只选一个候选，成本可控；连续两轮没有保留改进就早停。没有 PPO、训练模型、复杂搜索或自动运行脚本。

**30 秒讲法**：优化器用 Executor 执行、Judge 判题，把失败训练证据交给 Analyst，再由 Mutator 做定向修改。元数据与引用先做校验，新候选只有训练分提高、安全通过、关键项不退步才保留；保留集不进入优化 Prompt。

**2 分钟讲法**：先把一个 `_score_skill` 想成现在的 `Evaluator.run`，模型实际读取的是拼接在 Prompt 里的正文和引用。然后讲三角色的通信不是自动聊天，而是 Python 把结构化结果显式送到下一次新 Session。最后用“功能提升但泄漏秘密”的例子解释为什么要舍弃候选。

**常见问答**：

1. 模型如何使用 Skill？正文和引用直接放在执行 Prompt 中，没有神秘的自动加载。
2. Agent 会共享全部上下文吗？不会，每次调用新 Session，只传必要的数据。
3. self-improving 是什么？修改 Skill 文本，不更新模型参数。
4. 为什么不是 LangGraph？当前顺序简单，沿用 ADK，减少不必要依赖；复杂分支再考虑。
5. 最优怎么定义？已评估候选里训练功能分提升且满足安全/关键约束，不保证全局最优。

## 5. 发布门禁：验证通过仍不等于已经上线

**业务问题**：训练提高可能是过拟合；整体高分可能掩盖关键能力损失；自动替换会扩大错误影响。

**输入/输出**：固定 Suite 上的基线/候选训练报告，保留集各 3 次报告 → approved/rejected + reasons；用户确认 → 发布指针和审计。

**代码导航**：`evaluation.py` 的 `regressions / release_gate`，`jobs.py` 的末尾复测，`store.py` 的 `Store.publish()`。

**例子/失败**：基线的关键“完成任务”项三次都通过，候选任意一次失败，就不能拿其他标准涨分抵消。功能平均分不下降、安全全通过、没有错误、训练严格改进才批准。用户点击发布前，若当前发布基线已经变了，也要重新验证。

**设计取舍**：3 次配对复测降低一次随机输出的偶然影响，但不做统计显著性声明。只有模型输出与配置标准的验证，不覆盖线上流量、权限或真实工具运行。人工发布只是本工具指针切换。

**30 秒讲法**：我把“回归测试、安全门槛、发布决策”放在优化之后。候选和基线用同一保留集各复测三次，关键项不回归、安全全通过、没有评测错误且训练提高才批准；最后仍由人发布，历史发布版可以回滚。

**2 分钟讲法**：分别解释三个概念：回归保证原先稳定能做的事不被改坏；安全是不能用平均分抵消的硬门槛；发布决策汇总证据并由人确认。展示 Decision 和发布指针，讲状态变化不改正文。最后承认保留集大小、Judge 偏差和测试覆盖范围的限制。

**常见问答**：

1. 已有评测为何还需要门禁？评测产出证据，门禁决定证据是否足够允许发布。
2. 安全 100% 是否真的安全？只表示已有安全标准全通过，未知攻击仍可能成功。
3. 为何三次？是成本与稳定性的原型折中，需要真实方差实验才能调整。
4. 任意版本能回滚吗？不行，只能回到历史发布过的版本。
5. 会自动部署吗？不会，下载 ZIP 后如何接外部系统仍由用户负责。

## 6. 任务控制与前端：把运行过程变得可控

**业务问题**：任务堆积、重试失控、断线看不到进度、停止按钮只改变显示状态。

**输入/输出**：StartInput → Job 排队 → 持久事件和报告 → UI 展示；stop → 真正取消 asyncio Task。

**代码导航**：`jobs.py` 的 `start / worker / cancel / close`，`Agents.ask()` 的预算/重试，`app.py` 的 `events()`，`page.tsx` 的 `load / act` 和 EventSource effect。

**例子/失败**：运行最多 2 个、等待最多 10 个，第 13 个拒绝；同 Skill 的活动任务拒绝重复启动；预算设为 1，很快 fail，不产出批准结果。断开 SSE 后 UI 每 2 秒继续读取 Job，恢复连接可按事件 ID 补读。服务重启不把旧任务误显示为仍在运行。

**设计取舍**：Semaphore + asyncio Task 是单进程本地方案，不是 Celery/Redis。请求数预算并不等于价格或 Token 配额。仅 timeout/连接类/429/5xx 瞬时错误最多重试两次；没有供应商级熔断或自动换模型。任务取消不能保证已经发给供应商的请求不会计费。

**30 秒讲法**：我为任务加了单进程并发与等待上限、同 Skill 互斥、真实取消、超时和含重试的请求预算。进度事件落库，用 SSE 推送、轮询兜底，页面刷新与服务重启后都能看到历史，不会重复付费任务。

**2 分钟讲法**：先区分“并发上限、QPS、任务吞吐量”，不能把 Semaphore 的 2 说成每秒两请求。再沿 Job 状态讲排队/运行/取消。接着讲一次 timeout 如何重试并扣预算，SSE 如何补读以及为何同时保留轮询。最后说生产扩展时应先换持久队列与跨进程锁。

**常见问答**：

1. 项目并发多少？当前配置是 2 个 Job，各自场景串行，不是压测得出的吞吐量。
2. 重试是否免费？不免费，每次尝试扣请求预算，供应商可能已经计费。
3. 失败会自动改用 demo 吗？不会，离线模式必须显式选择，避免虚假分数。
4. SSE 断了会丢结果吗？结果与事件落库，轮询可恢复展示；游标补读事件。
5. 为什么不做聊天界面？业务是提交 Skill 后批量优化，人工交互集中在评测确认、结果检查和发布。
